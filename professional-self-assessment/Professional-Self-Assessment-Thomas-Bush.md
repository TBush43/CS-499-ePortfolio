# Professional Self-Assessment

Thomas Bush

I'm a platform engineer pursuing a software engineering career. Through my work, I've learned that a tool can function correctly and still slow people down when its user interface isn't clear. That's why I care about straightforward navigation, useful feedback, and making the next step easy to find. My computer science coursework has also changed how I approach a feature: I think about who'll use it, what data it needs, how it might fail, and who'll maintain it later. This ePortfolio shows that growth in working code and explains the decisions behind it.

My platform-engineering experience has made me attentive to the developers and other people who depend on shared systems. In CS 499, I've made my decisions reviewable through a code review aimed at peers or a manager, source comments, and narratives written for a broader audience. When my instructor asked for more code comments, I added short explanations of intent and non-obvious choices. The capstone was an individual project, so I can't claim it was team development. Still, explaining a decision, responding to feedback, and making the next developer's work easier are habits I'll bring to a team.

My testing and software development coursework taught me that edge cases and changing requirements aren't cleanup after the main feature works. I applied that lesson to the coaching priority feature. Instead of sorting the whole roster, I used maps to combine attendance, notes, goals, and follow-up flags by student ID, then a bounded priority queue to keep only the top three students for review. For *s* students and *r* related records, the selection takes O(s + r + s log k) time for a top-*k* list. The score includes readable reasons, so a coach can see why a student appears. Fixed-date tests cover ties, missing history, future records, and the 14- and 30-day boundaries. It's a coaching heuristic, not a prediction of an athlete's health or performance.

The software engineering and database work shows how my thinking moved beyond screens. The original CS 360 OnWeight app was a small Android prototype with static information and a login screen that didn't authenticate anyone. In OnWeight Coach, I separated activities, a ViewModel, service rules, and repository implementations. The final app supports a fictional student roster, training goals, notes, attendance, and follow-up actions. Four related SQLite tables keep those records across launches; foreign keys, indexes, bound query arguments, and transactions make the storage behavior explicit. I also moved database operations off the screen thread and added a confirmed delete action that removes a student's related records. Nineteen local unit tests pass. The Android database tests compile, but I haven't verified an on-device run yet.

Security coursework and my platform-engineering perspective have made me more careful about what an application promises. I removed the original SMS permission and misleading login, validated input, limited stored data to the coaching workflow, and excluded the database from Android backup and device transfer. These are meaningful improvements, but I won't present the prototype as safe for real student records. It doesn't have coach authentication, access control, or database encryption, so the portfolio and app tell users to use fictional information only. A feature shouldn't suggest privacy protections it can't provide.

The portfolio presents one artifact at several stages so the progression is visible. The code review identifies weaknesses in the original app; the design enhancement creates a usable workflow; the algorithm turns records into an explainable review order; and the database enhancement makes the records persistent. Together with the narratives, these pieces show how I communicate technical work, weigh an algorithmic trade-off, build a maintainable application, and consider security from the start. As I move from platform engineering toward software engineering, I want to keep building applications that are useful to people and honest about their limits.
