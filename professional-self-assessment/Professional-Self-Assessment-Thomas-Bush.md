# Professional Self Assessment

Thomas Bush

I work as a platform engineer and am pursuing a software engineering career. My Computer Science coursework has changed how I approach a feature: I now think about the people who will use it, the data it needs, the cases in which it can fail, and the developer who will maintain it later. Building this ePortfolio gave me a way to show that growth in working code and to explain the choices behind it. I am especially interested in mobile and full-stack applications, where a useful interface depends on sound software design and dependable data handling.

Platform engineering has made me attentive to the developers and other people who depend on a shared system. In CS 499, I made my decisions reviewable through a code review aimed at peers or a manager, source documentation, and narratives written for a broader audience. After my instructor asked for more code comments, I added short comments where they explain intent or a non-obvious choice. That feedback changed the deliverable. The code review, written explanations, and navigable portfolio also let different audiences evaluate the work without having to infer everything from source code. The capstone was an individual project, but these are habits I would bring to a team: explaining a decision, inviting review, and making the next developer's work easier.

My testing and software development coursework taught me to treat edge cases and changing requirements as part of the problem, not cleanup after the main feature works. I applied that lesson to the coaching priority feature. Instead of sorting an entire roster, I used maps to combine attendance, notes, goals, and follow-up flags by student ID, then a bounded priority queue to retain only the top three students for review. For *s* students and *r* related records, the selection takes O(s + r + s log k) time for a top-*k* list. The score includes readable reasons, so a coach can understand why a student appears. Fixed-date tests cover ties, missing history, future records, and the 14- and 30-day boundaries. This is a coaching heuristic, not a prediction of an athlete's health or performance.

The software engineering and database work shows how my thinking moved beyond screens. The original CS 360 OnWeight app was a small Android prototype with static information and a login screen that did not authenticate anyone. In OnWeight Coach, I separated activities, a ViewModel, service rules, and repository implementations. The final app supports a fictional student roster, training goals, notes, attendance, and follow-up actions. Four related SQLite tables keep those records across launches; foreign keys, indexes, bound query arguments, and transactions make the storage behavior explicit. I also moved database operations off the screen thread and added a confirmed delete action that removes a student's related records. Nineteen local unit tests pass. The Android database tests compile, although an on-device run remains to be verified.

Security coursework and my platform-engineering perspective have made me more careful about what an application promises. I removed the original SMS permission and misleading login, validated input, limited stored data to the coaching workflow, and excluded the database from Android backup and device transfer. These are meaningful improvements, but I do not present the prototype as safe for real student records. It lacks coach authentication, access control, and database encryption, so the portfolio and app tell users to use fictional information only. Recognizing that limit is part of the security outcome: a feature should not suggest privacy protections it does not provide.

The portfolio presents one artifact at several stages so the progression is visible. The code review identifies weaknesses in the original app; the design enhancement creates a usable workflow; the algorithm turns records into an explainable review order; and the database enhancement makes the records persistent. Together with the narratives, these pieces demonstrate my ability to communicate technical work, evaluate an algorithmic trade-off, build a maintainable application, and consider security from the start. They also show where I want to keep growing as I move from platform engineering toward software engineering: building applications that are useful to people and honest about their limits.
